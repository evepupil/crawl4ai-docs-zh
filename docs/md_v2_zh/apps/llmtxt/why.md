# 为 AI 助手赋能：我为 `crawl4ai` 优化 LLM 上下文的探索之旅

当我开始深入使用 AI 编程助手配合自己的库（尤其是 `crawl4ai`）时，我很快意识到，仅仅通过简单的 `llm.txt` 甚至增强版的 `README.md` 来提供上下文的方法远远不够。本文档阐述了我遇到的问题，以及我如何尝试为 `crawl4ai` 创建一个更有效的系统，让你（和你的 AI 助手）能够获取到精确无误的信息。

## 我对标准 `llm.txt` 文件的挫败感

在使用通用的 `llm.txt` 文件来处理像 `crawl4ai` 这样的复杂库时，我发现了几个痛点：

1.  **信息过载与焦点丢失：** 我发现，当我向 LLM 抛出一个庞大的、单一的整体上下文文件时，它常常难以应对。海量的信息似乎稀释了它的注意力。如果我询问一个关于小众功能的具体问题，LLM 可能会被库中更突出但当前无关的部分带偏方向。这感觉就像是在一本千页的小说中寻找一句话——信息确实*存在*，但 AI 并不总能正确地访问或优先处理它。

2.  **只有“是什么”，没有“怎么做”或“为什么”：** 我遇到的大多数 `llm.txt` 文件本质上都是 API 的转储——一份函数、类和参数的列表。这是库的“是什么”。但要真正有效地使用一个库，尤其是像 `crawl4ai` 这样灵活的库，你需要知道“怎么做”（惯用的使用模式、常见任务的最佳实践）和“为什么”（某些功能背后的设计 rationale）。没有这些，我注意到我的 AI 助手经常会生成语法正确但实际上效率低下或不符合习惯用法的代码。它是在*猜测*使用库的*意图*和*最佳方式*，而这些猜测并不总是正确的。

3.  **缺乏关于“像专家一样思考”的指导：** 静态的事实列表并不能教会 LLM 使用库的*艺术*。它无法传达经验丰富的开发者会考虑的权衡、他们学会避免的常见陷阱，或者组合功能来解决复杂问题的巧妙方法。我希望我的 AI 助手不仅能回忆起 API，还能帮助我*推理*出使用 `crawl4ai` 构建解决方案的最佳方法。

## 灵感来源：选择性包含与多维理解

我一直很欣赏像 Lodash 或 jQuery（在其模块化时代）这样的库，它们允许开发者只挑选他们需要的部分，从而产生更小、更专注的包。当我思考 LLM 上下文时，这种模块化和选择性包含的理念引起了我的深刻共鸣。当我只处理特定组件或任务时，为什么要强行向 LLM 灌输整个库的细节呢？

这引导我为 `crawl4ai` 开发了一种新方法：**多维、模块化的上下文**。

我不再使用一个庞大的 `llm.txt`，而是将 `crawl4ai` 的文档分解为：

1.  **逻辑组件：** 上下文围绕库的主要功能领域进行组织（例如，Core, Data Extraction, Deep Crawling, Markdown Generation 等）。这允许你只选择与当前任务相关的上下文。
2.  **每个组件的三个维度上下文：**
    *   **`_memory.md` (基础记忆)：** 这是“是什么”。它包含关于组件公共 API、数据结构、配置对象、参数和方法签名的精确、事实性信息。它是详细、明确的参考。
    *   **`_reasoning.md` (推理与问题解决框架)：** 这是“怎么做”和“为什么”。它包括设计原则、带有决策指南的常见任务工作流、最佳实践、反模式、解决实际问题的说明性代码示例，以及对权衡的解释。它旨在引导 LLM “像” 一位经验丰富的 `crawl4ai` 用户一样“思考”。
    *   **`_examples.md` (实用代码示例)：** 这是纯粹的“给我看代码”。它是一个可运行代码片段的集合，演示了使用组件功能和配置的各种方式，附带最少的解释性文字。用于快速查看不同的实践模式。

**目标：**
我的目标是为你提供一个灵活的系统。你可以给你的 AI 助手：
*   仅 **memory** 文件用于快速查询 API。
*   **reasoning** 文件（也许结合 memory）用于帮助设计解决方案。
*   **examples** 文件用于查看实际实现。
*   根据你的具体任务，**组合**使用一个或多个组件的这些文件。
*   或者，为了更广泛的理解，可以使用特殊的聚合上下文，如“Vibe Coding”上下文或“All Library Context”。

通过提供这些结构化的、多方面的上下文，我希望能显著提高你在使用 AI 编写 `crawl4ai` 代码时所获帮助的质量和相关性。以下部分将指导你如何选择和使用这些不同的上下文文件。
